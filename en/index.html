// depth −10 m · my development environment

Forge. One application, four modules.

I develop Forge, an application for agentic software development. The core takes work from an issue to a verified pull request. Research, analysis, verification and deployment come from four modules that are switched on individually.

core · 03 implementation

Forge

issue → verified pull request

It turns an issue into a job and runs it through the whole procedure: specification, implementation by an AI agent in a separate working tree, code review, tests and a pull request. Then it follows up on review comments, CI failures and merge conflicts.

Independent jobs run in parallel, dependent ones run in sequence, and larger deliveries run as missions across repositories. Where a person should decide, the job stops and waits. It is operated from the web, the terminal and Telegram.

Modules run inside Forge and share its interface and supervision. Each keeps its own approvals and evidence.

Four modules

Each module can be switched on, switched off, or left out of a delivery altogether. Its data stays when it is switched off.

module · 01 research

Bellows

idea → supported opportunity

Checks an idea before anyone analyses or builds it. It searches public sources, retrieves every cited page itself and checks that the quotation is really there. It proposes opportunities with evidence, counter-arguments and open assumptions; a person decides on each one. No opportunity is also a valid result.

research · verified quotations · decisions

module · 02 requirements

Anvil

intent → actionable brief

Tests a requirement against the real code and looks for ambiguity, gaps and impact across the application. It helps complete the brief, proposes a design and breaks a broad intent into separately deliverable parts. Larger deliveries are prepared as a mission and handed to the core once approved.

code analysis · requirements · missions

module · 04 verification

Temper

specific version → evidence

Verifies a change on the running application, independently of whoever wrote it. It walks through scenarios in the browser and through APIs, compares the result with the brief and keeps the steps, screenshots and other evidence. It can start the application under test itself across common stacks, from Spring Boot and .NET to Django and Rails.

acceptance · browser · API

module · 05 deployment and operation

Rivet

plan → verified deployment

Prepares a deployment plan under the environment's rules and waits for approval. After deployment it verifies the actual outcome, keeps the history and can roll back to the previous version. It also covers servers, scheduled interventions, incidents, and health and security monitoring.

deployment · environments · operations

Shared foundations

The core and the modules share one way of choosing models, one supervisor and one way of keeping requirements together with evidence.

Tool and model selection

Cognera Harness

Chooses the AI tool, model and reasoning level for each step by complexity, risk, context size and provider health. Rules can deny or limit a model; where needed, a person picks the agent.

Supervision and recovery

Supervisor

One independent process watches the core and the modules. It follows the work, keeps records of it and answers instructions. It handles operational problems only within the permitted scope and hands everything else to a person.

Requirements and evidence

CogneraSpec

Keeps the specification, tasks and evidence together. Every requirement has a task that fulfils it and a test or procedure that verifies it. Missing coverage shows up at proposal time, before any code exists.

Until November 2026 these were six separate applications. Merging them into one cut the operational overhead: one server, one interface, one supervisor. I keep developing Forge; deployment choices and the level of autonomy depend on the project, permissions and verified capabilities.

Related tools include Meeting Agent for turning meeting recordings into issue drafts, MCP integrations, and reusable development rules and skills.

Before we start

What is agentic engineering, and what does an agentic engineer do?

Agentic engineering is the design and construction of systems where AI agents use tools and carry out connected tasks. An agentic engineer handles the architecture, context management, permissions, testing and supervision of the result.

What can you help with?

Software development automation, multi-agent system design, bringing AI into an existing application, and connecting agents through APIs and MCP. A useful starting point is one process that is slow or hard to verify today.

Do we need to adopt all of Forge?

The scope follows your environment. We can start with one integration or one part of the development process. Forge modules are switched on individually, so you can begin with implementation alone and add verification or deployment later. Forge shows my experience and approach; we choose tools to fit the project.

Why one application with modules instead of six tools?

It used to be six separate applications. Each had its own server, its own supervisor and its own settings, so mostly the operational work grew. Today everything runs in one Forge process: the modules share the interface, model selection and supervision, but each keeps its own approvals and evidence.

How do you manage quality and autonomy?

We define scope, permissions, acceptance criteria and approval points in advance. Tests and review verify a specific version. Deployment has its own checks in the target environment.
